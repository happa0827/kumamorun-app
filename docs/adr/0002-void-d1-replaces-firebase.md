# クラウドは Firebase をやめ、Void + Cloudflare + D1 に移す

認証を自分のサイトで持ち、ディープリンクでアプリにログインさせることにしたため、Firebase Auth の利点がなくなった。アプリ向けの API をどのみち作るので、サイト・認証・API・DB を Void（Cloudflare Workers）と D1 に1つにまとめる。計画は `docs/plan/void-migration.md`。

## Considered Options

- **Next.js + Vercel + Neon**: 成熟していて情報が多い。だが、サイトと DB が別サービスになり、Void の「デプロイ1回で D1 まで作る」利点を捨てる。Void が使えなかったときの退路として残す。
- **Supabase**: Auth・Realtime・Presence が標準で揃う。認証を自作する以上、使う機能は Realtime だけになり、割に合わない。無料枠は1週間アクセスがないと停止する。1秒以内の切断検知が必要になったときの候補に留める。
- **Firebase のまま**: 認証だけ自作しても、Realtime Database の利点（`onDisconnect`、購読）はハートビートで代替でき、残す理由が薄い。

## Consequences

- Void は2026年10月に公開されたばかりで、成熟度に不安がある。計画の最初に小さな検証を置き（認証3種、ディープリンクのコード交換、D1 への書き込み）、結果で本実装に進むかを決める。Void が使えなくなっても、中身は Hono と素の Cloudflare Workers なので、ロックインは浅い。
- 切断の検知は、サーバー側の `onDisconnect` から**ハートビート**に変わる。アプリは20秒ごとにライブ状況を書き、サイトは最後の書き込みから60秒を超えたら停止とみなす。強制終了からの反映は最大60秒ほど遅れる（Firebase では1秒以内）。1秒級が必要になったら Durable Objects を足す。
- Firebase SDK だけが WebView に残る理由（`onDisconnect`）がなくなるため、クラウドとの同期は **WebView から Rust の HTTP クライアントに移す**。ADR 0001 の「Firebase は WebView に置く」は、この ADR で置き換える。ドメインと音を Rust が持つ点は変わらない。
- 進化の書き込みは、段階の更新と花の加算を**1つのトランザクション**にまとめる。ADR 0001 にあった「段階の書き込みの後、花の加算の前にアプリが終了すると花を失う」弱点が解消する。進化のルール（成長か開花か）は Rust が持ち、サーバーは不変条件の検査と原子的な書き込みだけを行う。
- アプリの認証は、サイトが渡す使い捨てコードを API で端末ごとのトークンに交換する方式にする。トークンは URL に載せず、Rust が OS の資格情報ストアに保管し、WebView には渡さない。端末ごとにサイトから失効できる。
- `users/{uid}/…` の形を `status-kumamorun` が読む制約はなくなる（サイト側も変えられる）。Electron 版（`kumamorun-app`）は使う人がいないため、扱わない。
- 既存の利用者（数人）のデータは、二重書き込みなしで移す。端末のローカル保存が正のままなので、新しい版の初回ログインで、ローカルのデータを自動でアカウントに取り込む。Firebase の最後の版には、保険として、データを書き出す機能を足す。
- 開発用のデプロイ済みサイトは作らない。開発はローカルの `void dev`（ローカルの D1）だけで行い、デプロイするのは本番の1つだけにする。
